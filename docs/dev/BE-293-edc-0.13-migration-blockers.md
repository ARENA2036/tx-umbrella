# BE-293 / ARENA EDC 0.13.0 preparation: unresolved decisions

This workspace is a local migration candidate based on clean ARENA `develop` commit
`f386f05e34d68d7753251d2b7fc009b7d1b738df`. It is not a complete Tractus-X 26.09 Umbrella lock and is not ready to deploy.

## Confirmed local migration

- Connector chart dependency is pinned to the 26.09 component-matrix version, `0.13.0`.
- Connector configuration uses `dcp.*`; `dcp.sts.dim` became `dcp.sts.div` and the credential service runtime variable uses the 0.13 `TX_EDC_IAM_DCP_CREDENTIALSERVICE_URL` name.
- Existing DID strings remain unchanged. BPNs move from `participant.id` to `participant.bpnl`; the existing DID moves into `participant.id`.
- Context IDs were copied verbatim from the separately preserved 0.12 candidate. They were not generated or replaced in this workspace. They have not been verified against live deployments and must be confirmed by the identity owner before any rollout.
- AP6 values remain byte-for-byte unchanged until its topology and identity mapping are established.
- A 0.13-specific chart patch requires Secret references for the management API key, dataplane proxy key, Vault token, and external datasource password; it fails rendering when a reference name or key is absent. No Secret names or keys are set here. The Provider Vault seeding Job also requires externally provisioned Secret references for its Vault token, signing private key, AES material, and each configured Vault seed alias. Seed-payload Secret keys must contain the KV-v2 request body expected by the endpoint. No credential values or Kubernetes Secrets are created by this migration.

The published 26.09 component matrix constrains EDC chart/application to 0.13.0, DTR to 0.13.0, BPDM chart/application to 7.1.0/7.5.0, and Holder Wallet and Issuer Service to 0.4.1. Those versions are not a complete Umbrella dependency lock; this change updates the EDC wrapper dependency and keeps other component pins visible as separate compatibility blockers.

## Local dependency and render validation

On 2026-10-29, the integration branch fetched the exact declared dependencies from their configured repositories. Locks are present for the Connector bundle, its `tx-data-provider` parent, Umbrella, and the nested DTR, data-persistence, and Identity & Trust bundles. `pgadmin4`'s existing `1.25.x` range resolved to `1.25.3`; other chart versions remain the exact versions declared in their charts. The repository dependency script applied the SecretRef patch to the exact Connector `0.13.0` package. The Connector `0.13.0` → bundle `1.2.2` → Provider `0.4.3` artifacts were rebuilt without changing those versions. The separate DTR TLS fix is integrated as its own change and has a regression test. Strict lint and the full EDC profile Umbrella render passed with synthetic SecretRef names/keys; the render was inspected in memory only and contained 240 resources, including the corrected DTR TLS Secret reference. A no-reference Connector render still fails closed. The Provider Vault setup mounts externally provisioned Secret files read-only and posts them as files; this does not verify any live Secret payload.

The pinned component set is not a full 26.09 matrix: this Umbrella still pins DTR chart/app `0.9.0`, while the 26.09 matrix lists `0.13.0`; it pins BPDM chart `6.2.0` whose downloaded package reports app `7.2.0`, while the matrix lists chart/app `7.1.0`/`7.5.0`. The current identity bundle contains `ssi-dim-wallet-stub` chart `0.1.14`, which is not demonstrated to be equivalent to the 26.09 Holder Wallet and Issuer Service charts `0.4.1`. These were not silently upgraded. The 26.09 release notes also call out BPDM data-cleanup requirements and the DTR Bitnami-to-Cloud-Pirates migration caveat.

## Security review: embedded key material

The Provider chart previously put signing-key and AES material in a rendered ConfigMap consumed by the Vault setup hook. The repository does not document that material as disposable test-only data. It is therefore treated as sensitive and unclassified, not presumed safe. The local candidate removes those fields from the ConfigMap and requires existing externally managed Kubernetes Secret references for the Vault token, signing private key, AES material, and configured seed payloads. The Secret volume is read-only; values have no defaults. This is a chart-source correction only: it does not read, create, overwrite, rotate, or remove live Kubernetes/Vault material.

The historical key remains in Git ancestry. If the security owner cannot confirm it is a disposable fixture, publication still requires an approved key-impact assessment and any needed history-remediation/rotation plan. This branch does not perform either action.

## Decisions required before a complete release candidate

1. **PostgreSQL and Vault topology:** Connector 0.13.0 declares optional PostgreSQL 0.18.3 and Vault 0.28.0 dependencies. The Connector subchart values explicitly set `install.postgresql=false` and `install.vault=false`, so those Connector-owned dependencies are disabled. Separately, the local `dataspace-connector-bundle` chart declares Bitnami PostgreSQL 15.2.1 and HashiCorp Vault 0.27.0 behind the bundle-level `postgresql.enabled` and `vault.enabled` conditions; this bundle's values currently set both bundle-level switches to `true`. An offline `tx-data-provider` Helm render with synthetic SecretRef names produced Connector PostgreSQL and Vault resources; this validates chart behavior only, not live infrastructure inventory. The current chart defaults therefore include bundle-managed PostgreSQL and Vault. It is **not established** that these services are managed externally or intentionally separated. The 26.09 component matrix does not define the Umbrella's full database topology or migration. The database/platform owner must confirm the intended topology and data/PVC ownership before any topology or chart-version change, and provide a tested, backed-up migration plan.
2. **Federated catalog data:** the 0.12-to-0.13 guide documents removal of the `edc_federated_catalog` table and associated configuration during migration. It describes setting `tx.edc.postgresql.migration.federatedcatalog.enabled=false` before migration when that table's data must be preserved. This setting is a migration safeguard, not proof that the old federated-catalog feature remains supported in 0.13. Before any DEV upgrade, the data owner must decide retain/export versus discard. If retaining, take a consistent PostgreSQL snapshot and a table-level export, restore both into an isolated disposable database, and rehearse the exact migration with the preservation setting before the live window. Compare schema, row counts, and application-visible catalog results after the rehearsal; define a restore-from-snapshot rollback rather than assuming Helm rollback reverses database changes. Keep the live database untouched until the owner approves the rehearsal evidence and retention outcome. The candidate intentionally does not set this option until the owner decides.
3. **Secret ownership and provisioning:** the Connector and Provider charts now require externally provisioned Secret references, but no Secret names/keys, content source, lifecycle owner, or runtime identity permissions are specified. Infrastructure/security must define who creates and rotates each referenced Secret and how environments supply the references. The signing key and seed-payload values are still present in the existing Git ancestry and unmodified profile value files; their owner has not classified them. The revised chart does not render those payload values into the Vault setup Job, but this does not erase Git history, sanitize the value files, or establish whether the live Vault keys are the same material. The profile values must not be published until their contents are classified and any required history remediation is approved. Do not rotate/delete live or historical identity material without the security/identity owner decision.
4. **Canonical context IDs:** values are copied from the 0.12 candidate, not derived anew. The identity owner must confirm those exact IDs are canonical and already bound to the intended operator/provider/consumer identities. A mismatch must block deployment; IDs must not be regenerated to resolve it.
5. **Complete 26.09 Umbrella baseline:** local locks now make the currently declared dependency graph reproducible, but they do not make it a 26.09 component set. DTR and BPDM pins differ from the 26.09 matrix, and IdentityHub chart equivalence is unresolved. Upstream Umbrella issue #436 remains open, and the published Umbrella baseline reviewed for this work is 26.03.02. The release owner must provide/approve the complete component matrix and migration decisions before calling this a 26.09 Umbrella migration.

## Validation boundary

The focused tests, strict EDC-profile lint, and full EDC-profile Umbrella render pass with synthetic Secret references. Real Secret names, keys, ownership, and provisioning are still undefined; the `values-external-secrets.yaml` path was not rendered because it requires a non-empty Vault credential input. The separate Wallet test fixture renders without the TLS overlay, but combining that fixture with the TLS overlay fails YAML parsing in the external `ssi-dim-wallet-stub` ingress template; this was not changed here. These local checks do not prove database upgrade safety, identity correctness, runtime compatibility across the full 26.09 matrix, Secret provisioning, or live Secret payload preservation. No live cluster, Vault, database, or identity operation was performed.
