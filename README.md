# Eclipse Tractus-X Umbrella

This repository contains an umbrella helm chart designed to simplify the setup and management of the [Catena-X](https://catena-x.net/en/)
automotive dataspace network, leveraging [Eclipse Tractus-X](https://projects.eclipse.org/projects/automotive.tractusx) open-source components. It supports end-to-end testing, sandbox environments, and integration with various Catena-X services.

The umbrella helm chart is located in the [charts/umbrella](./charts/umbrella) directory.

Have a look in the [docs](/docs) section for user manuals and guides.

## Alpha deployment (charts/alpha)

[charts/alpha](./charts/alpha) deploys the Tractus-X Portal with IdentityHub-based onboarding as one Helm release:
Portal 2.6.0, CentralIdP and SharedIdP 4.2.1, IssuerService and IdentityHub 0.4.1, BDRS 0.6.0, Vault, PostgreSQL,
a test mail server (smtp4dev), a did:web resolver and two Tractus-X EDC 0.13.0 connectors for end-to-end tests.
[values.yaml](./charts/alpha/values.yaml) holds portable defaults (`*.example.org`);
[values-test-tractus-x.yaml](./charts/alpha/values-test-tractus-x.yaml) is the Alpha environment on `*.test.tractus-x.com`.
Every component has a fixed `fullnameOverride`, so in-cluster URLs are plain Service names (`http://issuerservice:8086`).

Requirements: Helm 3.8+ or 4, kubectl, Python 3 (for `hack/alpha-identity.py`), openssl.

```sh
bash hack/helm-dependencies.bash      # downloads the dependencies and applies hack/patches (fail-closed)
NS=alpha
kubectl create namespace "$NS"
python3 hack/alpha-identity.py -n "$NS" secrets --execute          # identity Secrets (random values)
python3 hack/alpha-identity.py -n "$NS" secrets --edc --execute    # test connector Secrets
# create the operator-provided Secrets (table below), then:
helm install alpha charts/alpha -n "$NS" -f charts/alpha/values-test-tractus-x.yaml -f values-local.yaml
python3 hack/alpha-identity.py -n "$NS" vault init        # writes ~/.alpha-vault/vault-init.json (0600)
python3 hack/alpha-identity.py -n "$NS" vault unseal
python3 hack/alpha-identity.py -n "$NS" vault configure   # Vault tokens of IssuerService, IdentityHub, BDRS
helm upgrade alpha charts/alpha -n "$NS" -f charts/alpha/values-test-tractus-x.yaml --reuse-values \
  --set identitySeed.enabled=true                         # issuer setup and the Portal keys; restart the Portal backend
# after onboarding the two test participants through the Portal:
python3 hack/alpha-identity.py -n "$NS" vault configure-edc
python3 hack/alpha-identity.py -n "$NS" vault revoke-root
```

`values-local.yaml` is git-ignored: on the first install it sets the client secrets the Portal
stores in its own Secrets (`portal.backend.keycloak.central.clientSecret` = CentralIdP `sa-cl1-reg-2`,
`portal.backend.keycloak.shared.clientSecret`, `portal.backend.processesworker.bpdm.clientSecret` and
`.sdfactory.clientSecret` of the BPDM and SD-Factory service accounts). It also sets the cluster addresses
`networkPolicy.publicIngressCidrs` (public ingress load balancer) and `networkPolicy.apiServerCidr` (Kubernetes API
server, needed by the identity seed Job). Credentials and cluster addresses never go into tracked values files.

Operator-provided Secrets:

| Secret | Keys |
|---|---|
| `portal-registry-pull` | `.dockerconfigjson` (pull access to the Portal backend images) |
| `centralidp-keycloak`, `sharedidp-keycloak` | `admin-password` |
| `centralidp-postgres`, `sharedidp-postgres` | `postgres-password`, `password` |
| `centralidp-seeding-clients` | `miw`, `bpdm`, `bpdm-gate`, `bpdm-orchestrator` |
| `centralidp-seeding-service-accounts` | one key per service account client id (`sa-cl1-reg-2`, ...) |
| `sharedidp-seeding-cx-operator` | `initial-user-*`, `mailing-*` |
| `sharedidp-seeding-master` | `sa-cx-operator`, `sa-provisioning` |

Generated by `hack/alpha-identity.py`: `identity-postgresql`, `identity-db-users`, `issuerservice-superuser`,
`identityhub-superuser`, `bdrs-management`, `portal-bdrs`, `portal-identityhub` (keys written by the identity seed),
`edc-postgresql`, `edc-db-users`, `edc-provider-auth`, `edc-consumer-auth`, and the Vault tokens `*-vault-token`.

Maintenance: Vault starts **sealed** after every restart of its pod; IssuerService, IdentityHub, BDRS and the
connectors stop working until `hack/alpha-identity.py -n "$NS" vault unseal` has run. Keep the unseal keys outside
this repository. Running the identity seed again (new `identitySeed.runId`) rotates the Portal keys: restart the
Portal backend afterwards.

## Key Features

- **Automated Setup**: Provides a fully functional network with minimal manual intervention.
- **Modular Subsets**: Includes predefined subsets for specific use cases like data exchange, portal management, and business partner data management.
- **Extensible**: Easily integrates with additional components or custom configurations.
- **Cross-Platform Support**: Tested on Linux, macOS, and partial on Windows systems.

## Release Compatibility

The versions of the [integrated components](/docs/user/linux/installation/README.md#available-components) correspond to the overarching **[Release 25.09](https://github.com/eclipse-tractusx/tractus-x-release/blob/25.09/CHANGELOG.md#2509---2025-10-01)**

## Purpose

The Umbrella Chart is intended for:

1. **Testing**: Run end-to-end tests for Catena-X services.
2. **Sandbox Environments**: Create local environments to evaluate and experiment with Catena-X components.
3. **Development**: Provide a unified setup for contributors and developers working on Tractus-X projects.

## Cluster Setup

- Ensure your cluster meets the updated system requirements:
  - Kubernetes version `>1.24.x`
  - Helm version `3.8+`

For detailed setup instructions, refer to the [Setup Guide](/docs/README.md#setup-network--installation).

## Prerequisites

Running this helm chart **requires** a kubernetes cluster (`>1.24.x`), it's recommended to run it on [**Minikube**](https://minikube.sigs.k8s.io/docs/start/).
Assuming you have a running cluster and your `kubectl` context is set to that cluster, you can use the following instructions to install the chart as `umbrella` release.

> **Note**
>
> In its current state of development, this chart as well as the following installation guide have been tested on Linux and Mac.
>
> **Linux** is the **preferred platform** to install this chart on, as the network setup with Minikube is very straightforward on Linux.

> [!WARNING]
> As we do not currently test on Windows, we would greatly appreciate any contributions from those who successfully deploy it on Windows.

For detailed setup instructions, refer to the [Setup Guide](/docs/README.md#setup-network--installation).

## Testing GitHub workflows locally

If you want to try out your new or improved GitHub workflow locally, before pushing, you can try to use
[act](https://github.com/nektos/act). Follow the official [installation instructions](https://github.com/nektos/act#installation)
for your OS/package manager to set it up on your machine.

There is also plenty of documentation on how to use act and simulate events, that would trigger workflow runs on GitHub.
Some workflows might run into issues, when running them locally. This might be caused by missing values for
`${{ github.event }}` references. To fix this, you can provide your own [event](https://github.com/nektos/act#installation)
as `.json` file. There are already examples present in the [/.act](.act) directory.

An local example run via `act` could look like the following: `act -e .act/pr_event.json pull_request`
